## Findings and evidence

### OP-01 — High: Merchant cannot handle exact-item recovery or fulfilment problems

**Follow-up status (11 October): exact-item recovery offers and unavailable-item/general preparation reporting locally implemented and package/build verified. Return-receipt and settlement visibility are now locally implemented and package-tested; see the return/settlement follow-up for build verification.** The finding below records the original source audit. Restart durability and signed-in cross-role acceptance remain open.

Web `MerchantV1Opportunities.tsx` loads `recoveryOpportunities`, exposes exact-line failure/problem reporting and lets a replacement branch accept or decline an exact-SKU recovery offer. `dastakV1.ts:1971` parses separate fulfilment/recovery/return/settlement feeds; the current backend handler exposes `reportExactSkuFailure`, `respondExactSkuRecoveryOffer` and `reportFulfilmentProblem`.

Native `DastakV1MerchantClient.swift:432` decodes only `fulfilments` from that response. `DastakMerchantModel.swift:408` refreshes incoming opportunities, Food requests, fulfilments and legacy orders, with no recovery-offer lane or exact-item/problem commands. `DastakMerchantOrdersView.swift` has no corresponding controls. ### OP-02 — High: Native Delivery ignores current-generation return missions

**Follow-up status (11 October): typed return/completed lanes, native return custody controls, return-bound GPS and protected restart recovery are locally implemented; see Delivery implementation follow-up below.** The paragraphs below record the original source audit. Signed-in native acceptance is still pending.

### OP-05 — High: Retry keys do not always identify an immutable command

**Follow-up status (11 October): Restaurant menu, operating and media commands corrected within the running Merchant workspace.** Original payload/branch/version/key and upload bytes are frozen across uncertain retries; conflicting changes are blocked. Other Merchant/Delivery/Admin commands and process-restart durability remain open. The following paragraph records the original audit finding.

Native menu identity (`DastakMerchantModel.swift:222`) includes entity type/ID/version but not branch or payload. A timeout followed by a changed name/price at the same version reuses the retained key with different request details. Web `merchantMutationKeys.ts` explicitly fingerprints the payload. Native collection identity (`DastakDeliveryPartnerModel.swift:383`) similarly omits mission version, collection reference and failure reason; general mission identity omits package count, evidence path and reason. Some stock/selection commands generate a fresh key on every call. These are source-confirmed risks, not a tested claim that a specific production request duplicated or failed.

Required: retain an immutable pending command and key, distinguish definitive rejection from unknown outcome, block conflicting edits while resolution is pending, and reconcile the same command. A payload hash alone is insufficient if an unresolved original mutation may already have succeeded. Tests must include timeout then edited payload, same-command retry, known rejection, authoritative reconciliation and relaunch policy.

### OP-06 — High: Delivery exception reporting and independent heartbeat are absent

**Follow-up status (11 October): native problem/unreachable reporting and a foreground app-root heartbeat are locally implemented and package-tested.** The original finding follows. Heartbeat is for normal missions only; return liveness uses mission-bound GPS, not an invented return-heartbeat API. Device/background acceptance remains pending.

Native shows "contact Operations" after custody problems (`DastakDeliveryPartnerRootView.swift:633`) and exposes before-pickup cancellation, but does not call `v1ReportDeliveryProblem` or `v1ReportCustomerUnreachable`. Web provides reviewed recovery actions for those operations. Native has real `v1PublishLocation` support in `DastakActiveDeliveryTracker`; this is **not a finding that native GPS tracking is missing**.

Web additionally sends `v1Heartbeat` when a normal mission is active to preserve contact when precise GPS is temporarily unavailable (`DeliveryPartnerView.tsx:382`). Native refresh polls read snapshots, not this heartbeat. Local tracking SQL updates contact on accepted GPS samples; independent heartbeat absence can matter when no qualifying sample is published. Actual timeout/escalation behavior on a device was not tested.

Required: permission-gated issue reporting with custody safeguards and separate bounded heartbeat while an eligible mission is active. A heartbeat must not invent GPS coordinates or unlock arrival.

### OP-07 — Medium/high: Workspace selection/loading can misrepresent Merchant state

Web carries explicit branch context (`merchantBranchContext.ts`) and filters incoming/fulfilment/recovery feeds by the selected branch. Native Store chooses Restaurant whenever a menu exists, otherwise Retail, otherwise legacy (`DastakMerchantCatalogueView.swift:18`); no explicit branch/type switch exists. Initial Store and earnings requests swallow failures (`DastakMerchantModel.swift:168`), so an outage can leave a legacy fallback or no data without an accurate feed-specific error. Both types of snapshot are probed rather than selected from an explicit branch context.

Required: explicit authorized branch context, branch-scoped state/actions, stale-response guards, independent loading/errors/retry, and preservation of valid data. Do not infer that the backend permits every account to manage multiple branches; render only authorized branches discovered by the existing contracts.
