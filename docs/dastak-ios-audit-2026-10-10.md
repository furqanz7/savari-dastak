## Decision

**Continue the existing native platform, with a substantial Customer presentation/state rebuild and targeted parity work across all roles. Do not restart the entire project.**

The repository contains real SwiftUI applications and reusable API/domain infrastructure, not an empty prototype. However, the running Customer entry point is still the older native interface. The Reimagined reducer is implemented and unit-tested but not integrated into the native UI. iOS is **not yet equivalent to the accepted web product or certified release-ready**.

This document completes the broad source/configuration review and records successful Debug simulator builds for all three apps, **266 passing host-side package tests**, and **18 passing simulator app tests** (284 total; the Merchant/Admin app tests are placeholders). Initial storage/launch stalls were overcome sufficiently for warm simulator execution and limited Customer preview interaction. **The requested end-to-end product/runtime audit remains incomplete:** no full cross-role journey, physical-device delivery, signed distribution archive, or production order was certified by this audit.

## Findings, ordered by delivery priority

Severity describes impact on achieving the requested native product. Source-confirmed behaviour is distinguished from scenarios still needing runtime reproduction.

### IOS-01 — High: Reimagined is not the native Customer application yet

`DastakCustomerRootView.swift:15` defines Home, Orders and Account tabs and mounts the legacy SwiftUI screens. `DastakHomeView.swift` is a conventional catalogue interface. `DastakReimaginedState.swift:110` contains a separate reducer with Home/Orders/Profile/Settings and environment states, but searches of the native app/UI code found no integration of that reducer; its consumers are domain tests.

No native equivalent of the web's live supermarket/cafe/outdoor scene was found in these entry points. Launch videos and matte backgrounds are not that environment implementation.

**Action:** rebuild the Customer presentation/navigation layer around the accepted phone experience while preserving the existing authenticated clients. Decide the native rendering approach before porting the immersive scene. Do not assume browser assets or Babylon.js code are drop-in SwiftUI components, or promise identical high-end graphics/performance without device profiling.

### IOS-02 — High: location-aware availability is missing from native Customer UI

`DastakV1CustomerClient.swift:695` exposes catalogue/restaurants/order operations, but not the current area-availability or checkout-quote endpoints. `DastakCustomerModel.swift:510` fetches the canonical catalogue and legacy restaurant list without a versioned owned-address availability snapshot. `addToCart` at line 934 checks quantity limits, not local stock or serviceability. The native discovery radius defaults to 10 km (`:1544`) and uses a separate discovery-location concept, rather than the current fixed 30 km availability policy.

**Important:** shared backend admission checks still enforce stock and rider availability. This is a missing native UX/preflight layer, not evidence that iOS bypasses server security. See `20261008095639_customer_area_availability.sql:236` and `20261009131135_customer_thirty_km_serviceability.sql`.

**Action:** reuse the current backend availability contract; scope by account/address/version, expire stale results, show the area-not-serviceable state, gate stock additions, and block order placement when no eligible rider exists while allowing available items into the cart.

### IOS-03 — High: address changes do not invalidate/reload relevant Customer data

`DastakCustomerModel.swift:408`, `:442` and `:460` save/select/delete addresses but do not refresh restaurant discovery or availability. `selectDiscoveryLocation` at line 478 updates a different location without refreshing the V1 catalogue. The older restaurant endpoint uses an owned default address on the server, so native's displayed discovery location and restaurant data can diverge or remain stale.

**Action:** use one explicit delivery-location identity/version for serviceability, Food discovery and checkout; cancel/ignore replies for previous addresses and refresh after successful address changes.

### IOS-04 — High: closed restaurant state is decoded but not used to disable entry

`DastakV1CustomerClient.swift:213` includes `acceptingOrders`, `isOpen` and branch status. `DastakHomeView.swift:212` opens every returned restaurant with no corresponding closed-state guard. The menu also permits normal item selection. There is no matching closed-store presentation in that rail.

**Action:** preserve Admin-visible closed restaurants, show Store closed, disable restaurant entry as specified, and recheck current availability before submission. Reuse server-authoritative Admin visibility; do not hide restaurants merely because they are closed.

### IOS-05 — High: basket semantics differ from Reimagined

`DastakCart.swift:46` stores Grocery and Food in one cart, calculates one subtotal and creates one combined submission. `DastakCartView.swift:151` explicitly describes a Food + Retail basket. This is not the independent service-specific shopping/review behaviour in the current Reimagined state/web.

**Action:** introduce account-scoped separate carts with exact SKU and exact branch/item/option identities. Service switching must retain both carts, and checkout must consume only its submitted service/snapshot.

### IOS-06 — High: current cart and ambiguous submission recovery are not durable

`DastakCustomerModel.swift:96` owns an in-memory cart. Its persistence code (`:1483–1547`) saves discovery/onboarding preferences, not shopping. `v1SubmissionAttempt` and its idempotency key are also in memory. A process restart loses the local basket and any uncertain submission attempt identity.

The order list can discover an already-created server order after restart, but that is not a durable checkout journal and does not establish duplicate-safe recovery after a lost response. No duplicate order was created during this audit.

**Action:** persist minimal account-scoped shopping and a durable submission/recovery journal; reconcile server order state before retrying an uncertain submission. Keep prices, stock and payment truth on the server.

### IOS-07 — High: successful submission clears more than its submitted snapshot

`submitV1Order` sends the current lines and later calls `cart.removeAll()` (`DastakCustomerModel.swift:757–816`). Quantity controls remain separate from the disabled submit button. If shopping changes while the request is in flight, success can erase additions made after that request started. This is a source-level race; not a runtime reproduction.

**Action:** capture the submitted snapshot, subtract only those quantities after an authoritative success, and make success acknowledgement idempotent. The unused Reimagined reducer already has snapshot-subtraction logic; add duplicate-callback tests before integration.

### IOS-08 — High: delivery/platform fee estimates are absent before reservation

`DastakCartView.swift:147` shows subtotal and explicitly defers all delivery/platform totals until the basket is secured. Native has no equivalent of web `useCheckoutEstimate.ts`, which loads an address-and-basket-specific server quote with freshness checks.

The matching receipt does render server delivery/platform charges (`DastakV1MatchingView.swift:520`); this audit found a pre-reservation presentation/contract gap, not evidence that the backend 2% calculation is missing.

**Action:** add the current quote endpoint and freshness/address/basket invalidation. Show Platform fee without the percentage, say Tax is included, and do not recreate the fee formula independently on device.

### IOS-09 — High: Payments screen contradicts the current payment lifecycle

`DastakCustomerSavedViews.swift:207` selects payment history using `paidAt != nil`. Lines 250–287 promote Razorpay checkout, cards, net banking, wallets and Pay Later. Its activity list is limited to the first 12 loaded orders and labels them confirmed payments.

Meanwhile the native V1 confirmation screen (`DastakV1MatchingView.swift:1136`) correctly offers UPI/Cash on Delivery. Backend inspection confirms that this launch flow sets `paid_at` on successful doorstep collection (`20260828115505_dastak_v1_pay_on_delivery_launch.sql:962`), not merely on commitment. Therefore this audit does **not** claim that its `paidAt` filter mislabels unpaid launch commitments. The established problems are obsolete payment-method messaging and a limited order-derived history without full collection/refund activity detail.

**Action:** align Payments with the actual collection/refund records and current policy, distinguish due from collected/failed/refunded, add appropriate pagination/detail, and retain any historical provider flow only where genuinely supported.

### IOS-10 — High: native delivery tracking misses the new customer call feature

The server/web now expose `riderPhoneNumber` for permitted active-order tracking (`20260919093000_customer_rider_call_and_bill_repair.sql`; `CustomerLiveDelivery.tsx:31`). `DastakDeliveryTracking.swift:5` does not decode it, and `DastakDeliveryTrackingView.swift` has no call action. A legacy courier card elsewhere has `tel:` support; that does not fix V1 tracking.

**Action:** decode the authorized nullable number, validate it, show Call delivery partner in the active-order context, and remove access when the backend stops exposing the tracking projection.

### IOS-11 — High: Admin governance parity is incomplete

At the initial audit, native had real admin access, command center, network, catalogue editing, application approval, operational pauses, rider escalation, order tracing/cancellation and payout visibility, but lacked the current restaurant Customer-listing Remove/Restore operation. The local follow-ups below add restaurant listing controls, Merchant organization/branch governance and corrections, Delivery Partner suspension/reactivation, and read-only native audit history. Live acceptance and broader cross-role verification remain pending; this does not certify complete Admin parity. Native network identity detail remains largely read-only; the new controls are separate workspaces under More.

**Action:** map every current web admin capability to a native counterpart; port missing merchant/delivery governance and restaurant listing controls with reasons, version guards, consequence confirmation and audit visibility. Do not confuse listing removal with store closure or deletion of history.

### IOS-12 — High: operational UI and cross-role test coverage is insufficient

The first app test run stopped on disk exhaustion; two retries stalled on simulator launch. After a direct preview launch and warm simulator startup, Customer app tests passed (16), followed by Merchant (1) and Admin (1), all with zero failures. Separate Debug build-only checks also passed for all three apps. The Merchant/Admin app test files each contain only `XCTAssertTrue(true)` (`Apps/Dastak/Tests/DastakMerchantTests/DastakMerchantTests.swift:4`, Admin equivalent), so their passes do not exercise operational workflows.

All five relevant package suites passed on the macOS host (266 tests total), but the three shared app schemes list only their app test targets. CI runs Foundation/DesignSystem/Infrastructure/Domain package tests, not `swift test --package-path Packages/DastakUI`; simulator tests are opt-in (`.github/workflows/foundation.yml:121`). No XCUITest target was found. Package success does not fill this device/UI/cross-role coverage gap.

**Action:** make simulator execution reliable in CI and establish a controlled signed-device setup; include DastakUI in CI, add native UI/contract regression tests, and test the cross-role lifecycle rather than counting placeholder bootstraps as readiness.

**Current local follow-up (11 October):** the normal Swift package CI job now includes the DastakUI regression suite. Merchant/Admin placeholder bootstrap tests were replaced with real hosted privacy-resource tests in the prior slice. Operational screen automation and full cross-role lifecycle coverage remain unfinished. Simulator CI stays explicitly opt-in; no remote workflow was dispatched.

### IOS-13 — Medium/high: authentication failure classification needs hardening and device tests

The app uses real Supabase Apple/Google sign-in, profile bootstrap, authenticated clients, a shared token broker, nonce handling and identity checks—these should be preserved. But `AuthenticationClient.swift:413` maps every error while loading the current account/session to nil, and `restoreAccount` (`:223`) turns nil into signed out. A transient refresh/network failure can therefore appear as a missing session. Separately, `DastakCustomerRootView.swift:196` signs out on any session-registry 401 without a visible refresh-and-confirm retry at that boundary.

These are source-level failure-path risks, not a reproduced native sign-out loop. The web session incident does not prove the native apps have the same cause.

**Current local follow-up:** failure classification, bounded registry refresh/retry and late-restore protection are implemented below. After the approved narrow cache cleanup, 168 infrastructure tests and 181 UI/model tests pass, and Customer/Merchant/Admin Debug simulator builds all succeed. Live provider expiry, foreground/resume and actual revocation/role-denial checks are still pending. This finding is not closed as end-to-end verified.

### IOS-14 — Medium: native map supports search but not exact manual pin placement

`DastakLocationPicker.swift:75` shows a fixed Marker on a pan/zoom map. Panning does not update `selectedLocation`; no tap-to-coordinate/drag-to-position mechanism is wired. Selection comes from current location or `MKLocalSearchCompleter` suggestions (`DastakLocation.swift:166`).

**Action:** add a center-pin confirmation or draggable/tappable pin workflow with reverse-geocoding, correct freshness, denied-permission fallback and clear address confirmation. Keep the existing native MapKit/search foundation.

### IOS-15 — Medium: discovery completeness and startup work need improvement

`refreshV1Catalogue` loads the entire browse-map catalogue in 250-SKU pages, up to 10,000 products, while fetching only 50 restaurants with no native restaurant cursor. A restaurant failure can mark the combined catalogue refresh failed after Grocery data has loaded. Bootstrap concurrently fetches legacy orders/parcels as well as V1 data even though Parcel is a Soon service.

**Action:** separate resources/failures, load needed catalogue pages/rails lazily, support current nearest-Food pagination, and profile startup/network/memory on a real phone. Search and pack grouping must be checked in every discovery surface, not only product details; the detail card already supports related pack choices.

**Current local follow-up:** initial Grocery discovery now fetches one 250-SKU page; selected browse-map destinations/rails load matching categories on demand. Food has independent failure/loading/retry state and nearest-page pagination. A Food menu transport failure no longer clears valid Grocery area/stock/rider availability. Saved-product and reorder lookup are deferred until those features are used, with bounded pagination and exact-SKU preservation. See the startup follow-up below for verification and remaining gates; this is not real-phone performance certification.

### IOS-16 — Medium: Merchant/Admin app privacy manifest packaging is incomplete

Read-only project parsing shows Dastak bundles `PrivacyInfo.xcprivacy`, but Merchant and Admin resource phases bundle only Assets. The shared app manifest declares UserDefaults reasons and relevant collected data; the two other binaries do not explicitly include that app-level declaration.

**Action:** review each binary's own data/API usage and include the appropriate manifest in each target. Verify the final archive and dependencies' manifests; a valid source plist alone is not App Store privacy certification.

**Current local follow-up:** Merchant and Admin now include the existing shared app manifest in their resource phases, matching Customer. Hosted app tests check the bundle-root manifest and existing tracking/UserDefaults declarations in all three targets. This fixes the omitted resource, not a completed per-app data-practice review or signed Release archive certification. See the privacy-packaging follow-up below for verification.

### IOS-17 — Release gate: signing, push and distribution remain unverified

The project has bundle IDs, development team configuration, icons and Apple sign-in entitlements. Push registration distinguishes permission from successful device registration and is account-bound. However, `SignInWithApple.entitlements` specifies development APNs while native environment selection follows DEBUG versus Release (`DastakNotificationPreferences.swift:25`). Distribution signing can affect final entitlements, so the signed product—not just source—must be checked.

The Merchant app handoff falls back to an App Store search URL, not a verified product listing. This audit did not inspect App Store Connect/TestFlight, signed archives, provisioning profiles, APNs provider settings, OAuth allowlists, universal links, crash/analytics operations or an installed release's provenance.

**Action:** validate signed Release archives for all three targets, actual Apple/Google return flows, APNs foreground/background/cold launch, account switching/revocation and the intended distribution path. Do not claim these are broken merely because they were not verified.
