## Evidence and implications

### M-01 / M-02: reliability is the first slice

- [Journal](../Packages/DastakUI/Sources/DastakUI/DastakMerchantCommandJournal.swift:3) has only `.recovery` and `.restaurant`. [Model](../Packages/DastakUI/Sources/DastakUI/DastakMerchantModel.swift:793) uses in-memory `actionKeys` for normal incoming acceptance/decline, packages, Ready evidence and Ready. Evidence-path cache at line 101 is in memory. Retail add/count creates fresh keys at lines 632 and 655. Batch selection edits clear their retained key; the retained key alone does not freeze the entire uncertain command.
- [Global lock](../Packages/DastakUI/Sources/DastakUI/DastakMerchantModel.swift:171) includes any unresolved Merchant journal; a pending menu/recovery action can pause unrelated normal changes across the workspace. That is conservative rather than unsafe, but requires usable recovery and explained scope. Do not simply bypass it.
- [Current recovery](../Packages/DastakUI/Sources/DastakUI/DastakMerchantModel.swift:175) is explicit/manual on retry; acknowledgement cleanup, corrupt-file preservation and account checks already exist and should be reused. Do not erase unresolved records to make a banner disappear.
- [Refresh aggregation](../Packages/DastakUI/Sources/DastakUI/DastakMerchantModel.swift:276) awaits Orders, Store, Earnings and notification work. Orders coalesces refreshes and awaits its lanes. Legacy Store and Earnings use `try?`, so failed refreshes can leave old/absent data without a feed-specific explanation. Restaurant and fulfilment/recovery reads already have generation guards; retail/legacy/incoming do not have the same comprehensive latest-response policy.
- [Shared transport](../Packages/MarketplaceInfrastructure/Sources/MarketplaceInfrastructure/FunctionClient.swift:191) retries transient errors up to three total attempts; URLSession has 20-second request and 30-second resource limits, and auth token loading is bounded separately. These are not proof of an infinite network request. However, native Merchant does **not** use [Delivery's 12-second UI deadline/single-attempt adapter](../Packages/DastakUI/Sources/DastakUI/DastakDeliveryRequest.swift:12), or Delivery's immutable auto-recovery workflow. Multiple attempt/refresh stages can hold `busyIdentity` much longer than a business action should.
- Web is not automatically the safety specification: [web incoming keys](../Web/MarketplaceWeb/src/MerchantV1Opportunities.tsx:290) omit some editable payload fields, live in component memory and are not a restart-safe command journal. Improve that shared risk when implementing normal-command recovery rather than copying it into native.

### M-03: source-confirmed scroll reset

[Orders](../Packages/DastakUI/Sources/DastakUI/DastakMerchantOrdersView.swift:133) applies `.id(orderDeskLayoutRevision)` to the entire ScrollView. The revision includes queue, loading and request/fulfilment status plus pickup/tracking phase. The comment explicitly intends to reset scroll state. This is the same class of interruption the owner reported during Delivery testing; it is a source-established Merchant risk, not a newly reproduced live Merchant incident. Individual version-based card IDs and draft state also need review, not just the outer ScrollView.

### M-04: location selection is an authorization context, not a third name

[Native root](../Packages/DastakUI/Sources/DastakUI/DastakMerchantRootView.swift:6) has Orders/Store/Account with no selected store/location. [Store dispatch](../Packages/DastakUI/Sources/DastakUI/DastakMerchantCatalogueView.swift:18) chooses Restaurant if any menu exists, then Retail, then legacy. Both Store probes run at bootstrap, and the chosen catalogue/menu branch is reused internally rather than selected by the merchant.

[Web root](../Web/MarketplaceWeb/src/MerchantOrdersView.tsx:47) discovers verified branches, persists an account-scoped selection and passes it to Store and Orders. [Branch discovery](../Web/MarketplaceWeb/src/merchantBranchContext.ts:47) probes existing contracts and classifies operationally discovered locations; it is not a complete all-locations API. Any implementation must avoid claiming it discovers every authorized inactive location without a complete contract. Native onboarding already has [Legal business name / Customer-facing name](../Packages/DastakUI/Sources/DastakUI/DastakMerchantApplicationView.swift:524); retain those semantics.

### M-05: full order requires merchant-safe projection

Both platforms render sizeable inline operational cards, but no dedicated Merchant detail route/client was found in the active roots and cards. [Native fulfilment DTO](../Packages/MarketplaceInfrastructure/Sources/MarketplaceInfrastructure/DastakV1MerchantClient.swift:28) provides merchant line values, preparation/evidence/capabilities, branch, reports and rider projection; much of the first detail screen can be built from it. [Current handler](../Backends/Dastak/supabase/functions/dastak-v1-orders/handler.ts:614) lists Merchant fulfilments with only a limit; it has no dedicated detail selector in this audited flow.

Do **not** reuse Customer `get` or Admin execution-trace authority for Merchant. The audited [Customer get implementation](../Backends/Dastak/supabase/migrations/20260820180723_dastak_v1_batch_1b_commands.sql:719) asserts Customer actor and uses Customer order projection. A new merchant-safe historical/detail read, if needed, must authorize the relevant organization/store at the server, preserve price/PIN/privacy boundaries, and be an additive contract compatible with Build 61. This audit did not query live schema or deploy a new endpoint.

### M-06: native aggregate is not web Royalty parity

Native [History card](../Packages/DastakUI/Sources/DastakUI/DastakMerchantOrdersView.swift:122) reads [older merchantSnapshot](../Packages/MarketplaceInfrastructure/Sources/MarketplaceInfrastructure/DastakEarningsClient.swift:22) and shows completed/this-week/pending values. It does not have a dedicated Earnings tab or Merchant-organization Royalty client. Web [RoyaltyPanel](../Web/MarketplaceWeb/src/RoyaltyPanel.tsx:20) uses available/lifetime/negative balances, subjects, adjustments, payout destinations and withdrawal status/retry. The [earnings handler](../Backends/Dastak/supabase/functions/earnings/handler.ts:88) distinguishes legacy aggregates from `merchantRoyaltySnapshot` and exposes payout availability. Existing native Delivery Earnings code is Rider-specific; parameterize safely or add Merchant-specific requests, not a cosmetic role-label swap. Runtime/provider availability and live payout authorization remain separate.

### M-07 / M-08: menu editing and drafts

[Native menu](../Packages/DastakUI/Sources/DastakUI/DastakMerchantRestaurantMenuView.swift:17) has no search state or search control. Existing options at line 269 are displayed as text, while only creation of an option and group-level activation is provided. New MULTIPLE groups hardcode maximum 20. [Web editors](../Web/MarketplaceWeb/src/MerchantV1CommerceControl.tsx:370) edit individual option name/price/status and creation allows a group maximum. Native [dish editor identity](../Packages/DastakUI/Sources/DastakUI/DastakMerchantRestaurantMenuView.swift:198) includes entity/media version, so refresh remounts `@State` fields. Web [versioned draft reconciliation](../Web/MarketplaceWeb/src/restaurantMenuDraft.ts:17) preserves dirty edits and requires explicit resolution. Neither platform's current UI exposes the full category/group rename/reordering/required-choice experience; classify that honestly as shared UX scope if included.

### M-09 / M-10: discovery and completeness

- Native [browse-map route](../Packages/DastakUI/Sources/DastakUI/DastakMerchantCatalogueView.swift:77) takes precedence whenever a valid map exists. Its map root renders destination buttons, not search results; `query` filters only after a destination is selected. The All products/My storefront picker is in the alternate category route, not the normal map route. This makes the always-visible search field and scope behaviour incomplete.
- Native loads 5,000 SKUs and decodes `truncated`, but the native Store source never renders it. Web [limit warning](../Web/MarketplaceWeb/src/MerchantV1CatalogueControl.tsx:289) exists, although its client-side filtering still cannot recover products omitted by a cap. Neither should claim full-catalogue search without pagination/server coverage.
- Current [fulfilment-list SQL](../Backends/Dastak/supabase/migrations/20260916060000_include_released_merchant_history.sql:2) selects newest fulfilments across active and terminal states before applying its global maximum 100. It has no active-first exclusion/filter/cursor in this contract. Both clients can therefore omit an older still-active fulfilment under sufficient history volume. Return/recovery/settlement collections in the same SQL are not capped by this fulfilment limit; do not incorrectly describe all four feeds as limited to 100.
- Native [queue classification](../Packages/DastakUI/Sources/DastakUI/DastakMerchantOrdersView.swift:18) explicitly handles RELEASED and terminal order statuses but not fulfilment `COMPLETED`; web [classification](../Web/MarketplaceWeb/src/merchantOrderPresentation.ts:10) handles both COMPLETED and RELEASED. An order already terminal is handled by native; the missing explicit COMPLETED case matters when order-level state is not yet terminal. Existing native test covers `orderStatus: DELIVERED`, not this distinct condition.
- Native History truthfully labels its bounded window; that is an implemented disclosure, not a missing one. Full searchable history still requires a contract change, not just an unlimited local list.

### M-11 / M-12 / M-13: feedback, alerts and polish

- Native dish save/option-add guards return silently for invalid prices; enabled controls do not consistently reflect all validation. [Photo picker](../Packages/DastakUI/Sources/DastakUI/DastakMerchantRestaurantMenuView.swift:306) similarly returns silently on unreadable/unsupported media. Its inspector supports JPEG/PNG/WebP, not common iPhone HEIC; Ready evidence separately accepts HEIC. Improve conversion/feedback without inventing upload success.
- Native [preparation stepper](../Packages/DastakUI/Sources/DastakUI/DastakMerchantOrdersView.swift:493) is 1–20; web declaration validation accepts 1–1000. Verify server constraints before choosing one consistent UI range. A legal smaller UI choice needs a product reason rather than being accidental parity loss.
- Retail stale/permission/nonapplicability failures can be swallowed while Restaurant failure text leads Store fallback; do not label a successful Retail store as broken merely because the account has no Restaurant. Distinguish expected type mismatch, access denial, offline and service failure.
- [Merchant push delegate](../Apps/Dastak/Sources/DastakMerchant/DastakMerchantApp.swift:64) persists only a boolean “open Orders”, ignoring specific target identifiers. That is a queue fallback, not targeted order navigation. The setup model has a genuine 15-second Apple callback watchdog and explicit server-registration failure state; preserve it. [Read-only route gate](../Backends/Dastak/scripts/check-merchant-notifications.sql:2) covers eight Merchant event types; it was inspected but **not run against production**. No live sent/delivered timing or duplicate/missed test is claimed.
- Native Store banners are small editing previews, many dish fields are inline, some controls are mini-sized and use horizontal fixed-width panels. These establish polish targets, not a claim of a particular visual defect reproduced on a phone. Design a calm operational workspace around the task, not a copy of Customer's immersive shopping panel.

## Safe implementation sequence

1. **Reliability first (M-01–M-03):** protected ordinary-command journal, bounded request/reconciliation ownership, feed recovery and stable scroll/input. Reuse proven Delivery mechanisms where their semantics fit, without editing Customer/Delivery paths by default.
2. **Workspace and details (M-04/M-05/M-10):** explicit authorized store/location context; concise cards; full Merchant-safe detail read/screens and reliable active/history discovery. Develop additive backend changes locally, preserving Build 61 contracts; production migration/deployment requires separate authorization.
3. **Store/menu (M-07–M-09/M-11):** useful search/scope, completeness/error presentation, editable options, versioned dirty drafts and clear keyboard/photo/price feedback.
4. **Earnings (M-06):** typed Merchant Royalty read and truthful history/balance UI first. Any financial mutation is durable and gated by existing server availability. No activation of a provider or real payout.
5. **Finish visual/notification/distribution layers (M-12–M-14):** design pass and regression tests, then separately requested device/cross-role acceptance and Merchant distribution. Widgets/Control Centre/Shortcuts/Live Activities are not inferred Merchant requirements from Customer's feature set; consider them only for an explicitly useful Merchant task.
