## SC-01 — Wishlist omissions and state races (locally fixed)

Source evidence: web `ReimaginedWishlist.tsx` maps every saved identity to a row and Remove even when product/menu data is not loaded. It distinguishes `ready` from empty/error and provides a saved-item open action. Native `DastakCustomerSavedViews` previously rendered resolved products/dishes only, with an aggregate unresolved count, and tested `wishlistItems.isEmpty` after any first-read outcome. `refreshWishlist` had no loaded/failure/read-generation state; mutation responses replaced the whole list, allowing late reads or concurrent different-item responses to undo displayed changes.

- Added explicit loaded/failure states and stale-read/account-lifetime guards. Failed reads retain known entries, not a fabricated empty-ready result. Existing in-flight failure/empty handling is separate from saved-content resolution failures.
- Every unresolved saved product/dish is now an individually identified row with explicit Remove. It remains labelled **not resolved in the loaded catalogue**, not conclusively deleted/unavailable. Removal does not depend on catalogue lookup or stock, and always sends `wished: false`, never a stale toggle that could turn Remove into Save. The existing authenticated RPC supports removal of no-longer-listed entries. No endpoint/schema was invented.
- Resolved products open the existing Customer detail overlay with known product/pack data. Saved dish details/options open the existing restaurant menu focused at the exact saved item; unavailable restaurants remain gated. Focus/overlay wiring is implemented but actual scrolling/visual acceptance remains pending.
- Saved-state responses are validated for unique composite kind/ID and requested membership. Concurrent acknowledgements overlay their own exact results on returned snapshots, preserving both local actions while incorporating remote saved entries. An old read cannot overwrite a newer explicit change, and an account reset invalidates old work. Unknown responses keep prior state and report an error rather than guessing success.
- Wishlist entry and explicit refresh now include local availability, with no forced network refresh when the existing snapshot is still fresh. The bounded on-demand product/menu resolver is unchanged: there is no exact-SKU lookup in the inspected Customer API, and this change does not scan more pages or claim that unresolved entries have been fully checked. New save toggles wait for an initial verified list; the synthetic preview uses its known empty fixture. Prices remain estimates until checkout rather than promising a fresh price read for every Add.
- Added **15 synthetic regression tests** for failed versus empty readiness, unresolved removal by kind/ID, explicit false removal after another removal, failure retention/busy release, duplicate/composite identities, stale reads, out-of-order additions/removals, remote-entry incorporation, wrong receipts, unread toggle gating and reset-before-late-read. No actual Wishlist data changed.

## SC-02 — Order again independent-basket and local-availability safeguards (locally fixed)

Original source finding: web `ReimaginedCustomerRoot` reviews which service to rebuild for mixed historical orders and checks current local stock/restaurant eligibility before replacing only the chosen service basket. Native `DastakOrdersView.reorder` decided whether to confirm based on the **currently active** `model.cart.isEmpty`, not the basket targeted by the old order. `DastakCustomerModel.reorder` reconstructed all matching Grocery/Food lines into a temporary cart and could replace both baskets for mixed history. It added Grocery directly through `rebuilt.add`, without that path calling `groceryAddIssue`; its global pending-checkout guard also did not express a service-specific decision.

These were source-confirmed gaps, not a reproduced production incident. Shared server admission checks remain in place; the native UI gap does not imply a backend security bypass.

Local implementation now captures an immutable service-specific review before replacement consent. Mixed historical orders require Grocery/Food selection, unsupported/ambiguous lines are rejected, and only the selected basket can be replaced. Consent checks the target basket even when another service is open; the convenience path cannot silently replace a nonempty basket. Account, address/version, both baskets, active service and a context revision are rechecked after awaited reads. Editing and then restoring identical contents, switching services back, or reloading the journal invalidates old consent. Pending target-service reservations and unresolved confirmation for the source order block this action; unrelated-service reservations survive it.

Fresh Grocery lookup uses only the existing catalogue endpoint, 250 per page, at most 40 pages, stopping when the exact requested packs are found. It never substitutes stale cached/search products or historical prices. Food reloads current location-scoped menus and uses the existing bounded resolver for additional pages. Fresh owned-address availability is required in real account mode, including exact aggregate local stock, serviceability and restaurant-open checks. No rider still permits a basket rebuild but does not bypass existing order-placement gating. Quantity bounds, inactive/missing dishes/options, duplicate choices and required/minimum/maximum/SINGLE option rules are checked. All-or-nothing replacement matches the inspected web flow: unavailable data, expiry, transport failure or failed journal persistence leaves prior baskets intact; no partial quantities or skipped-pack substitution. Current prices are estimates until checkout.
